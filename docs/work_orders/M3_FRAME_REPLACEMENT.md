# M3 compulsory Frame replacement

Status: IN_PROGRESS; DoctorDoctor-scrapping application implemented offline.
Defeat's destroyed-Frame integration remains NOT_RUN. This is part of M3C/M3D/M3E/M3H,
not a new milestone or an authorization to deploy unfinished rules.

Source: DoctorDoctor Planned Obsolescence, book PDF 71 / printed p.69, and
destroyed Frame under Defeat, PDF 29 / printed p.27. Optional paid Frame Swap,
PDF 16 / printed p.14, is a distinct rule. Do not silently use its price or its
one-Asset/one-rule retention for compulsory replacement.

The owner ruled that the current Handler specifies each replacement package and
the player must choose a different Frame playbook. Compare official identities,
including JANUS/JANUS-B normalization; a cosmetic alias is not a different Frame.
The owner also ruled that compulsory replacement is free. Never charge Permissions
or reuse Frame Swap's price. Current replacement work remains blocking until its
actual package and application commit. The DoctorDoctor path now implements this
workflow, with unsupported optional abilities or additional Void work kept explicit.

## Work and authority

1. Retain the immutable originating cause, prior Frame identity, work revision,
   character identity and source deadline. Doctor scrapping requires immediate
   replacement; the Defeat destruction branch becomes applicable at the next
   explicit Off-Duty trigger. Wall-clock time never satisfies that trigger.
2. The affected player proposes a different core Frame using a native selector.
   Opening a menu is not agreement. Disabled ancillary rules cannot be granted.
3. The current appointed Handler specifies an exact package bound to that proposal,
   its revision and the current character/Frame generation. List every supplied
   Frame Asset, description, damage/Void state and any additional unlocked rule.
   Validate the printed cap, mandatory intrinsic setup and source availability.
   Never make up an Asset count, retain old Frame equipment, or copy paid Frame
   Swap benefits as a fallback. Optional rules require their actual implemented
   dependencies; unimplemented branches fail closed.
4. The player reviews the exact free package, required setup and
   canonical consequences, then explicitly confirms it. Changed package, Handler,
   chosen Frame or character state invalidates the old form/approval. Declining
   or revising a proposal never erases the compulsory replacement obligation.
5. Collect any playbook-specific human setup through owned durable tasks. This
   includes Prince fanbase choices, distinct JANUS Core state, CONSUME hunger and
   Red Queen Court coordination where applicable. Do not reuse stale creation
   snapshots or choose an external player's response for them. Persist runtime
   entities with stable IDs; preserve their distinct authority and privacy.
6. Apply the reviewed replacement exactly once through the canonical engine state.
   Preserve Girl resources, Identities, Bonds, prior receipts and private notes;
   audit every authorized difference. Reset/retire Frame-specific state according
   to the supplied package and printed exceptions. Record mandatory Void/other
   consequences rather than bypassing them. Complete work only after its actual
   mechanical effects and required setup apply.
7. Update public profile/Frame labels and safe owned Discord roles through the
   existing transactional projections/outbox. Keep the canonical profile revision
   consistent so valid later Plays do not become stale, and never reactivate a
   character to accomplish a Frame change. Discord delivery retries do not repeat
   the mechanical replacement.

## Required acceptance tests

- Doctor eight-box and Defeat destruction causes remain distinct; no early Defeat
  replacement before the explicit Off-Duty trigger, timer replacement or reroll.
- Own proposal only; appointed current Handler package only; exact owner acceptance.
  No administrator/private-note override, forged target or stale package acceptance.
- Same-playbook rejection includes canonical aliases; core/ancillary module guards.
- Synthetic case-by-case packages have no hidden default Asset count or price.
  Enforce five Frame Assets, required intrinsic Assets and supported rule grants.
- Independent cases for each core Frame's setup, control, counters and reactions;
  missing Prince/Core/Court setup cannot be acknowledged as finished.
- No old Frame Asset/ability leakage or Girl-resource reset. Preserve received
  coordination from other Frames unless a printed rule actually changes it.
- Exactly-once state, work, receipt and delivery intent under duplicate/concurrent
  submissions, with rollback, campaign isolation, backup/restore and rebuild.
- Pause and saved-read behavior, changed Handler/package/profile invalidation,
  safe cosmetic retry and subsequent valid Play after successful replacement.
